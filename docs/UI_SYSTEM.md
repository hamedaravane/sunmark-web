# UI system

## Direction

The public game name is **Sunmark**, pronounced **سان‌مارک** in Persian. `src/brand.ts` supplies the shared product name and description for runtime UI, tutorial welcome, and Vite/PWA metadata. The menu title renders Sunmark as an explicit LTR English text run inside the Persian RTL layout; the smaller eyebrow includes the Persian pronunciation. Keep names as runtime text. The preserved gold sun-rosette emblem remains the app mark.

The current **royal expedition** direction supersedes both the carved-stone controls and the restrained contextual-dock treatment. The interface is a colorful mobile game: lapis, turquoise, emerald, coral and amethyst enamel; warm parchment; polished gold settings; ivory dice; sun seals and stepped wing inlays inspired by Achaemenid craftsmanship. Different materials distinguish functional roles. The board and existing illustrated art remain the foundation. There is one integrated visual system, with no theme selector. See [ROYAL_EXPEDITION_REVIEW.md](design/ROYAL_EXPEDITION_REVIEW.md) for real-screen captures and validation.

All visible UI surfaces are Phaser Graphics: menu frame, buttons, player chips, progress pips, resource trays/cards, construction cards, trade selectors, modal frames/backdrops, scroll indicators, and destination lists. Labels are Phaser Text using runtime Persian strings. Ornament and victory art remains cropped Phaser Images; resource Images share a small atlas generated from code. Trading uses shared procedural scale geometry at 28/64 pixels. No Persian text is baked into assets and ownership color remains runtime data.

## Layout targets

- Mobile portrait first: 390 × 844 CSS pixels. The game shell fills the viewport on phones, tablets and desktops; device safe-area insets reduce the content region while the background extends behind them. The menu panel stays bounded at 440 pixels and dialogs at 640 pixels so text and controls remain readable on larger screens.
- `responsiveLayout.ts` selects compact landscape at 560 pixels wide when width exceeds height. At least 1100 × 700 pixels enables a dedicated desktop composition: an 80-pixel public player header, a 340-pixel private command panel, 24-pixel gutters/gaps, and a bounded island. The composition is centered and capped at 1520 × 1040 pixels; land is capped at a 66-pixel hex radius. Portrait tablets retain the stacked layout. ResizeObserver observes the independent outer shell for mode selection and the board for camera geometry. See [Desktop tabletop experience](DESKTOP_EXPERIENCE.md) for dimensions, interaction decisions, and review limits.
- The shell is fixed to the top of the viewport. A shared `--app-height` uses dynamic height in browser tabs, with a `100vh` fallback and a `100vh` override for standalone apps. Installed iOS apps with a translucent status bar can under-report dynamic/visual viewport height; do not subtract safe-area insets from the canvas or compensate with a device-specific offset. Match/menu controls retain their own safe-area padding; the footer's Phaser fill extends through the home-indicator inset. Dialog and portrait limits use the same shell height. The document fallback color matches the current stone footer. See [WebKit 254868](https://bugs.webkit.org/show_bug.cgi?id=254868) and [WebKit's safe-area guidance](https://webkit.org/blog/7929/designing-websites-for-iphone-x/).
- The portrait grid has a 124-pixel captain/opponent header, flexible board, 48-pixel contextual ribbon, 66-pixel resource shelf, 84-pixel action ledge and 6-pixel bottom spacing. Below 360 pixels wide or 720 pixels high, header/resources become 112/60 pixels. There is no separate End Turn row. Safe insets belong to the entire composition. The semantic `match-controls` grid shares these tracks without intercepting board input. In compact landscape, the header stays fixed above a scrollable rail with a 60-pixel resource shelf; all controls remain reachable on short screens without shrinking their touch targets. Header/footer materials stay within that rail rather than covering the board.
- `matchGeometry.ts` reserves 104 pixels of lower ocean for standalone dice on taller portrait boards. Below 420 pixels of available board height, portrait dice move to the action ledge and the entire board region fits the island. In landscape, dice occupy their own space in the control panel, leaving the entire board region available for land and coastal clearance. Desktop adds the shared size cap without changing the board center or input projection. The same board geometry applies before/after a roll and during placement. Dice are 48/56 pixels; the small-screen interaction keeps its full semantic target.
- Three dimensional action seals use amber construction, turquoise trade and violet development cards. A larger gold capsule follows the required primary decision. Controls have at least 48-pixel touch height, readable short labels and separate selected, pressed, disabled and keyboard-focus treatments. Location selection replaces ordinary tools with destination-list access and clear/cancel. Mandatory human decisions remain accessible during opponent turns.
- Opening setup uses the same preview/confirmation controls and in-dock destination list as later placement. Initial pieces are labeled free, paid-build/trade workspaces remain unavailable, and the required road is anchored to the just-confirmed settlement. Unselected starting settlement sites use small intersection markers instead of dozens of full building previews. The first ordinary turn belongs to the highest opening roller; the header remains human-owned. See [OPENING_SETUP.md](OPENING_SETUP.md).
- Placement exposes an in-game destination-list button alongside clear/cancel in the dock. It never covers land or port markers. The list previews a legal target, closes, and leaves final confirmation on the main screen. Tile inspection also has an in-game list reached from Pause → Game Review. Native dropdowns are absent from the visible interface.
- One Phaser game, one full-shell canvas, three scenes: backdrop, inset board camera, full-shell interface. CSS and ResizeObserver measure the board region independently. `Scale.NONE` uses an explicitly sized backing buffer at device pixel density, capped at 3× and four million pixels for mobile fill rate. The canvas keeps the shell's CSS size; `rendering/displayGeometry.ts` and `display.ts` project CSS coordinates through physical camera viewports, leaving layouts and touch targets unchanged. Browser resize and resolution-media-query changes refresh density. The HUD is never scaled with the fitted board.
- `fitBoard()` fits the radius-two island (5√3 radii wide, 8 high) with 40 pixels of ocean clearance on every side, without zoom or panning. The base fit is uncapped; desktop `matchGeometry()` then applies its 66-pixel radius ceiling. At 390 × 524 the land remains approximately 310 × 286; on shorter screens and during placement, the additional board height prevents unnecessary shrinking. Width still limits the largest complete island, including its ports. RTL does not mirror geography.
- Buttons have explicit line heights. Enamel feet, inner highlights and shadows fit within or immediately below their measured controls; pressing lowers the face. Menu and close controls retain at least 48 × 48 targets, with a discoverable gear and Persian «منو» label in the HUD. Sheet headers start at 66 pixels and grow for wrapped titles.
- The human captain keeps a prominent portrait, name, own score/target medal and acting-player status. Long human names may wrap over two lines. The latest public dice and a visible menu seal share this row. Three opponents (two in legacy saves) occupy a separate portrait row with public scores, owner rims and ten progress marks. The acting opponent is highlighted. Every player opens their real details; hidden opponent points and hands never enter this projection.
- Resources are collected objects on a shared enamel shelf, with individual resource-colored plinths, 24/29-pixel illustrations, prominent exact counts and short Persian names. These are passive inventory, visually distinct from resource selectors in sheets. Confirmed gains/spending retain the stationary highlight, exact delta and bounded flights.
- Detail rows wrap in two flexible columns; construction headers may wrap; trade controls use explicit line heights and narrow-screen padding. The menu centers safely when it fits and remains scrollable without losing its top on shorter screens.
- The nine 32-pixel port islets sit 20 pixels offshore, within the 40-pixel board margin. See [PORTS.md](PORTS.md).

## Rendering and input ownership

- `scenes/BackdropScene.ts` covers the menu with the preserved palace image and matches with a procedural ocean. `rendering/ProceduralOcean.ts` caches a bounded-resolution shader material at 30 Hz, with a generated Canvas/Graphics fallback; it pauses in menus, modal panels, hidden tabs, and reduced-motion mode. The original ocean PNG is a preserved reference, not a runtime download. See [GAME_BACKGROUND_PLAN.md](GAME_BACKGROUND_PLAN.md).
- `scenes/GameScene.ts` owns the inset board camera, terrain, coast, pieces, ports, previews, and board effects. Its camera size and semantic board surface share measurements. `rendering/boardInput.ts` listens to that surface and transforms client positions into camera-local coordinates.
- `ui/GameHud.ts` assembles **transparent semantic controls** and responsive layout nodes. These are the input/accessibility adapter: real buttons, labels, a live region, and a native modal dialog preserve keyboard navigation, screen-reader content, focus trapping, and scrolling. Their labels and state come from the local session. CSS opacity hides their visual output without removing semantics or hit areas. Name entry uses a transparent native input for Persian IME, autofill, and the phone keyboard. Its value is mirrored into an aria-hidden layout span; Phaser paints that measured runtime text, focus border, caret, and selection using browser text ranges. Name-sheet input DOM is preserved across unrelated platform updates to keep composition and selection intact. No visible input layer is added above the canvas.
- `ui/InterfaceScene.ts` paints the same layout as Graphics, Text, and preserved Image crops. The stage is pointer-transparent; semantic buttons dispatch through `GameHud` into the existing session. The canvas is decorative in the accessibility tree, preventing duplicate announcements.
- `ui/graphicsTheme.ts` supplies reusable enamel/parchment/gold/ivory materials. Rounded faces use bounded gradient strips, a shaded foot, setting, and upper highlight, without masks, texture downloads or randomness. `ui/royalArt.ts` supplies resource/card palettes, stepped wings, card frames, the menu crest and gear. `styles/global.css` holds semantic foundations; `styles/royal.css` owns the current composition and typography.
- `ui/headerModel.ts` projects public standings and computes a full-width header backdrop from canvas y=0 through the measured header bottom, filling top/side safe insets with the same lapis material. Controls retain the match grid’s safe-area padding. `ui/playerIdentity.ts` supplies stable seat avatars, robot names, and bounded/normalized player names; `ui/playerAvatarArt.ts` draws original human/robot enamel seals with runtime owner-colored rims, without bitmap downloads or brand artwork.
- `ui/graphicsComponents.ts` applies the materials to every control/card/panel, including pressed, disabled, selected, active-player, and keyboard-focus states. Selected choices have a contrasting bronze outline/rosette on light stone and warm gold on dark panels; focus has a separate outer ring. Victory progress derives from the core player summary and match target.
- `ui/semanticText.ts` measures browser-wrapped text by line so Phaser retains Persian shaping, bidi digits, inline labels, and responsive wrapping. Text crops honor overflow regions and texture resolution. `textGeometry.ts` computes baseline/reading-edge positions and ellipsizes constrained labels in logical reading order. The scrollable modal content uses a Phaser 4 external Mask filter in WebGL and a Graphics geometry mask in Canvas; the header and portrait stay outside it. Do not use `setMask()` for WebGL: Phaser 4 ignores that Canvas-only API.
- Repaint only after layout/content/focus/press/scroll changes. Stable Text/Image objects are reused, while removed semantic nodes release their objects. The observer excludes Phaser's own hidden RTL text canvases. Effects animate separately through bounded tweens.
- `ui/bottomSheet.ts` owns native modal semantics, close/Escape/backdrop handling, focus restoration, and independent content scrolling. Normal sheets may supply a fixed footer, painted outside the body mask, for trade summaries and confirmation actions. Its visible shell, shade, heading, controls, and scroll thumb are drawn in Phaser.
- `ui/sheets.ts` describes construction, bank/ports, player/tile/port details, history, help, target/inspection lists, results, and unfinished-trade warnings. `ui/components.ts` supplies escaped semantic markup and art identifiers.
- `ui/session.ts` owns the fixed human seat, confirmed state, guarded human/bot command entry points, open sheet, uncommitted trade/placement drafts, notices, latest transition, and the last 100 events. Confirmed state, history, and tutorial memory are persisted through the optional local MatchStore; no online projection is implied.
- `ui/botTurns.ts` paces independently validated bot commands every 650 ms, pausing ordinary turns for sheets, hidden pages, or updates, while allowing replies to human offers in the domestic sheet and cancelling stale state callbacks. No animation completion drives a rule command.
- `ui/GameFeedback.ts` consumes confirmed transitions once; `ui/GraphicsFeedback.ts` draws finite resource flights, delta labels, focus/confirmation emphasis, and victory sparkles/glint. `ui/motion.ts` shares live visibility/reduced-motion preferences. There are no visible DOM animation layers. See [ANIMATION_DESIGN.md](ANIMATION_DESIGN.md).
- `rendering/pieces.ts` retains orthographic Graphics settlement/city/road geometry and arbitrary ownership colors. The `?demo=pieces` page remains an isolated developer gallery, not part of the game UI. See [PIECE_RENDERING.md](PIECE_RENDERING.md).

## Interaction and language

- Persian RTL throughout; resource order is wood, brick, wheat, wool, stone in RTL reading order.
- The captain score and resource hand remain fixed to this device’s controller. The turn subtitle and active opponent seal follow the acting seat. Tapping a player opens details with private data only for the human. Opponent details show public score, total resource count, buildings, roads and played Knights.
- Default ownership colors remain blue `#438bff`, rose `#ff526e`, cyan `#26d4e8`, and violet `#c16bff`, supplied by `core/game.ts`. The renderer accepts arbitrary `Player.color` values.
- The unified resource hand belongs to the human on this device. Exact counts, icons, and labels stay visible during bot turns. Bank/primary mutation controls are disabled until the human’s turn; construction stays inspectable with human-only costs and turn explanations; domestic offers/responses to the active bot are available after its roll/Ahriman resolution; inspection, history, and help remain available and pause bot pacing through the native modal.
- The contextual dock groups a small hammer, trade scales and a development-card stack with short labels alongside one primary action. Before the human roll, large dice and any eligible pre-roll card affordance take priority; owned cards and planning remain inspectable through personal details. Mandatory choices hide ordinary actions. Trading has Player and Bank/Ports tabs. Domestic trading is available during any action phase, restricted to the acting opponent off-turn; bank/port controls remain human-turn-only. Negotiation keeps separate final consent with a human balance preview. See [DOMESTIC_TRADING.md](DOMESTIC_TRADING.md).
- Construction shows compact resource-icon holding/cost chips, checks and explicit shortages, points or remaining road supply, blockers and legal targets. Detailed tables and purpose explanations remain expandable. A player-selected goal persists with the match and compares readiness after trade payment and receipt. Choose a type, preview a highlighted target or use the list, then confirm. Cancellation pays nothing. The 15-road supply is enforced by core rules.
- Ahriman destinations also need preview and confirmation; clearing a selection never bypasses required relocation.
- Bank trading stacks give/receive cards, defaults to the best core-derived 4:1/3:1/2:1 payment rate, permits eligible rate alternatives, and shows exact payment/receipt and resulting balances before confirmation. Draft choices survive sheet dismissal; ending a turn warns only if a pending trade would be discarded.
- Port access derives from coastal buildings. Owned-port chips, all-nine-port directory, port details, and owned-port payment shortcuts retain their existing behavior. Each directory control is at least 48 pixels high. Placement picking takes priority over port inspection.
- Directly tapping the dice handles rolling; committed faces briefly pop and travel to the header without gating actions. On short screens, dice occupy the lower ledge instead of shrinking the island. The gold primary seal follows required resolution, Confirm Placement, End Turn, Declare Victory or Results. Missing targets disable confirmation; rapid double taps cannot end a turn immediately after building.
- Tapping a tile opens production number/probability, Ahriman status, and adjacent-building details. Pause → Game Review → tile list provides keyboard access. Required next actions take priority in the context strip; live notices announce confirmed feedback.
- Results retain the original victory emblem, winner, settlement/city score breakdown, final-board inspection, and return to menu.
- Animation never gates a command or changes state. Reduced motion removes travel and victory sparkles and keeps deltas stationary. Sheet entrance is a short opacity fade so drawing and semantic hit regions remain aligned.

## Installation and recovery

The menu has exactly Play and Tutorial, using emerald and amethyst enamel respectively. Play resumes an unfinished save or requests a name for a new four-seat match with Anahita enabled by default. Tutorial opens a separate disposable practice board without replacing the saved match. Play also resumes companion progress without restarting lessons. Replacement confirmation precedes name entry; canceling either leaves the prior save intact. Blank names default to «بازیکن», names are limited to 24 characters with whitespace/control normalization, and runtime markup escapes them. Names persist with the existing match snapshot; Play resume never asks again. Installation guidance appears in a dismissible app modal once on non-standalone startup, never as an extra menu button. The pause menu opens that app workspace and returns to the main menu. A downloaded release opens a dedicated update confirmation once, in the menu or during gameplay after the current sheet closes. Later dismissal keeps the update reachable through Pause → App without adding a third menu action. All new surfaces use the existing Phaser Graphics/Text renderer, native modal, and semantic controls. Browser installation prompts require an explicit tap; iPhone users receive Share → Add to Home Screen instructions. Updates download in the background. Confirmation saves the current match, activates the waiting worker, and reloads into the new release; an unavailable save blocks updates during unfinished matches. Another open page offers its own confirmation and never reloads automatically. `pwa/updateFlow.ts` owns prompt timing and save-before-update behavior; platform checks run on launch/resume/reconnection and every five minutes while visible and online. Resuming restores confirmed state and narrator memory without historical animation or unconfirmed drafts. Storage errors remain visible without blocking play. See [PWA_RELEASE.md](PWA_RELEASE.md).

## Typography and verification

Domestic negotiation pins the human's complete resource hand in a `SheetContent.context` slot between the heading and independently scrolling body. `InterfaceScene` paints this context on the modal layer outside the body mask, as it does the footer. The resource strip shows only the human’s resource names, icons, and counts; it has no building-goal controls or planning guidance. Payment warnings and final balance review stay specific to the proposed exchange, without exposing opponent hands. See [DOMESTIC_TRADING.md](DOMESTIC_TRADING.md).

Self-hosted Vazirmatn Regular (400), with Tahoma/Arial fallbacks, supplies both semantic measurements and Phaser Text via `UI_FONT_FAMILY`. `index.html` preloads it and `loadUiFont()` completes before Phaser starts. No extra font weights are shipped. `rendering/sharpText.ts` rasterizes interface, board, port, and feedback labels at the canvas density: font sizes, metrics, padding, and strokes are multiplied, then the Text object is inverse-scaled to retain CSS dimensions. Keep `Text.resolution` at 1: the installed Phaser 4.0.0 RTL path uses backing-canvas width in a scaled context when resolution exceeds 1, shifting or clipping Persian text. Increasing raster font size avoids that bug without editing Phaser. Font bounds are measured from the loaded Persian font and `textGeometry.ts` aligns each label to its browser baseline, accounting for rounding at raster density. Explicit font metrics and padding refresh when responsive text size or density changes; ellipsis and crop calculations convert between raster and CSS units. Parchment and gold use dark plum ink; colored enamel uses warm light text. Light-text enamel faces start at approximately 4.55:1 or greater against the main label color; the bright accents remain at edges, away from small text. Disabled controls desaturate the face while keeping readable labels. Overflow cropping honors both axes, including wrapped captain names.

The user performs interactive/device testing. Agent verification uses low-cost TypeScript checks, scoped lint/format checks, and focused pure layout/unit tests in Node. The automatic production pipeline runs full checks and builds after authorized pushes to `main`; monitor that run as part of a publishing task. Do not launch a browser without an explicit request. Tests cover density budgets, physical camera projection/culling, CSS input alignment at integer/fractional densities, raster text scaling, baseline/reading-edge alignment, inline font-size alignment, ellipsis, target preview/confirmation, Ahriman relocation, inspection IDs, and coordinate agreement between inset-camera input and resource-flight anchors; they do not claim to validate CSS viewport behavior, visual appearance, or native-modal behavior on devices.

`tests/responsive-layout.test.ts` also covers phone/tablet/desktop layout selection, larger portrait boards, and complete island/port clearance with input-coordinate round trips in landscape, including phone safe insets. Device review should include portrait and landscape, resizing during placement, scrolling the short-screen control rail, and opening trade/narrator dialogs at mobile, tablet and desktop widths.

## Shared match presentation

Offline and online matches both mount `game/matchRuntime.ts` and the same
GameHud, GameScene, InterfaceScene, BackdropScene, feedback and native sheets.
Authority is a session adapter concern: local GameSession runs rules and bots;
OnlineSession sends authenticated intents and reads a private server projection.
MatchSession/MatchState define the presentation boundary without inventing unknown
opponent hands or deck contents. The online room renderer serves entry/lobbies only.

The canvas and background always cover the full viewport. Desktop bounds apply to
the tabletop/control composition, never to the canvas origin or backdrop size.
All match input and Graphics measurements use the shared canvas/viewport coordinate
path, including device-pixel-ratio changes. See ONLINE_PLAY.md for adapter ownership,
privacy, retries, feedback and validation.

Desktop Anahita conversations sit at the bottom of the island area, with a larger
full-body illustration in the left column and the RTL dialogue beside her.
The illustration meets the viewport's bottom edge; only the dialogue panel keeps
the 24-pixel bottom gutter (or a larger device safe-area inset).
The dialogue body scrolls independently while its actions stay in the footer.
The desktop composition uses the same shared layout variables as the tabletop;
phones retain the existing stacked portrait and bottom sheet.

Account onboarding uses native semantic HTML forms above the existing palace
background, with the royal lapis, turquoise and honey palette. This preserves
password-manager/autofill behavior, secure masked password entry and native mobile
keyboards without adding credentials to canvas text objects. Form presentation
lives in `account/markup.ts`; the controller owns submission and focus. Inputs are
16px and touch targets at least 48px. A two-step registration groups introduction
and account details, with an optional undisclosed gender and a one-time recovery
key. Account profile fields never appear in public match UI. Match presentation
continues to use the one shared Phaser runtime in both modes.
